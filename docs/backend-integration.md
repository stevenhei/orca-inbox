# Decision Inbox backend integration

The worker registers the panel and isolated editor requests in [backend-protocol.ts](../src/backend-protocol.ts). It persists decisions, accepted replies, unfinished delivery attempts, drafts, and policy as a versioned state in Orca plugin storage. A single worker serializes each read-modify-write transaction. It stages chunks in the inactive slot and atomically switches a small index, keeping up to two generations within Orca's quota. Each metadata generation has a 1 MiB admission budget. Every unanswered question reserves space for an initial answer, an idempotency record, an outbox entry, delivery status and a receipt, plus a draft record with an attempt ID for each verified participant. The reservation covers 4 KiB of content per draft and per initial answer, measured as escaped UTF-8 in Orca storage, with record and identifier overhead budgeted separately. Larger valid content, follow-ups, and settings use shared capacity and can return storage unavailable. Once a reply is accepted, its retry and receipt are included in the accounting. Existing generations can continue with up to 1.25 MiB of physical metadata per slot while their accounted size exceeds the regular budget, provided the write does not increase their accounted size. Dense older generations can still exhaust this bounded migration space. Shared package fields are stored once. Immutable snapshot chunks are stored separately with a combined 2,500,000-character base64 budget. Both an eventual native owner adapter and the Inbox must use that same writer or move the acceptance transaction to a shared host-owned store.

- List and detail apply caller access before sorting, filtering, or returning decision data. Workspace scope uses host and workspace IDs. Paged row projections omit review content and use the reviewing desktop's supplied IANA time zone. Search runs against the source decision before projection. The legacy list and full detail use a 768 KiB response budget. New detail writes reserve room for receipt growth within that budget.
- The first accepted initial answer is committed with its delivery obligation before any transport call. A racing answer receives the recorded winner. An identical submission replay returns the recorded answer. Changed content or binding under a used ID returns `conflict`.
- A reply awaiting receipt remains `submitted` after transport custody. Confirming receipt requires verified proof tied to the recorded reply and original Chat. Interrupted sends become `undelivered` on startup and wait for an explicit retry. Retry uses the original destination and reply ID. The native adapter must deduplicate that ID at the destination.
- A submission adapter supplies trusted participants, image bytes and initial grants, and versioned text for evidence selections. Chat access matches the exact host, workspace, and session. Attachment IDs identify an immutable version. A live adapter rechecks the exact snapshot grant for reads, annotations, and retry. The worker authorizes private images separately and redacts inaccessible evidence and annotations. Snapshot responses fit the panel bridge by limiting base64 to 900,000 characters per image.
- Drafts are scoped by owner and question. Draft writes require the revision returned by the prior read or write, including when clearing. Partial notes may contain empty text until submission. Keep the same attempt ID across ambiguous submit results. Refetch after the empty `inbox.changed` event. Settings carry a revision and scope repo overrides to canonical IDs returned by `settings.repos`.

## Installed Orca integration boundary

The worker resolves a plugin-local principal from the host-supplied desktop panel or editor context and the authorized local workspace inventory. The development request shim is a host-admin development surface. The installed plugin is served through the desktop bridge. The principal can save Inbox-owned drafts, answers and settings. Orca native owner activity is separate.

The [versioned skill and CLI](../agent/decision-inbox/SKILL.md) produce an explicit Chat record and a local lookup hint. The worker uses supported Orca CLI reads to verify the hinted exact session and workspace and the last assistant message of the completed exchange. The bounded read must also contain the preceding user boundary. The CLI returns no turn ID, so older exchanges are outside this check. Intake accepts link evidence. Private agent snapshot access requires a verified upload/grant adapter. Native Items are read-only through the authorized local Bot CLI. The worker opens a reference containing only a question ID or settings selector in the focused local workspace through the public editor API.

Orca mail from the installed plugin remains unavailable on the inspected headless host. A saved reply can be undelivered. Mail acceptance remains submitted, and a verified acknowledgement is required to mark it received. See the [current handoff](implementation-handoff.md) and [Phase 2 native parity audit](native-integration-audit.md).

## Wide-tab diagnostics

Review and settings use the focused local workspace from the worker's `workspace.readContext` and require an exact, unique `workspace.list` match. Orca 1.4.271 derives both worker IDs from the same projection. It uses a host-qualified `identity:` key where available and keeps `folder:` keys for folder workspaces. The worker sends the selected ID and a workspace-relative reference path to `editor.open`. Orca resolves that ID again in its desktop window's workspace inventory. [Orca 1.4.271 host API](https://github.com/stablyai/orca/blob/v1.4.271/docs/reference/plugin-host-api.md#editoropen) · [Renderer workspace lookup](https://github.com/stablyai/orca/blob/v1.4.271/src/renderer/src/components/plugins/view/plugin-view-host-actions.ts)

An unsuccessful open returns an `unavailable` result with a sanitized stage and code. The worker logs `[wide-tab] review` or `[wide-tab] settings` with that stage and code, as in `editor.open: not_opened` or `file materialization: EACCES`. On the same desktop runtime, `orca plugin logs PLUGIN_KEY --json` retrieves those lines. The in-panel `getDecision` and `settings.get` requests depend on their existing authorization and do not need editor navigation.

## Local verification

Run `npm test` for TypeScript, Orca's local plugin harness, plugin checks, and the DOM smoke test. `orca plugin validate . --json` validates the current manifest. The regression suite includes duplicate and concurrent acceptance, crash after transport custody, restart, same-ID retry, paired host routing, invalid and verified receipts, bilingual search, private evidence, draft persistence, and scoped settings.

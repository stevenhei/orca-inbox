# Native Orca integration audit

The Inbox V1 release depends on Orca providing authenticated submission from ordinary workspace Chats, one authoritative owner-answer operation shared with native **Needs you**, and verifiable receipt of each reply in its original Chat. Desktop and paired-server acceptance is deferred by the owner. This audit used command discovery and source inspection.

## Evidence and versions

| Environment | Observation |
| --- | --- |
| Stock PATH CLI on this machine | `orca --version` reported **1.4.264**. The bundled plugin guide describes Host API **1.10**. The stock command registry and matching source lack Bot Item commands. [Host API at v1.4.264](https://github.com/stablyai/orca/blob/v1.4.264/docs/reference/plugin-host-api.md) |
| Coordinator runtime | Reported **1.4.271**. The development handoff records “Plugin service is not available” in that runtime. [Design handoff](design-handoff.md) |
| Bot-only command wrapper | Successfully listed Items from this bot chat, as reported in the follow-up. That observation establishes a working bot-context read through the wrapper. It does not establish an Item command in the stock PATH CLI or any ability to call it from an ordinary workspace Chat or plugin. |
| Upstream source | Inspected Orca at commit `374693b1414ad73e8c41846b715cd04e026db118`. The pinned links below refer to that snapshot. The separate [upstream plugin API request #48010](https://github.com/stablyai/orca/issues/48010) reports a similar gap on 1.4.272. |

## Minimum upstream interface proposal

These are proposed semantics. The operation names are illustrative.

| Operation | Minimum behavior |
| --- | --- |
| `submitFromChat(input)` | Accept a request through an Orca-issued Chat-scoped invocation. Resolve immutable origin and access grants, then create or recover one native Item binding per question. |
| `readDecision(binding, after?)` | Return the canonical answer state and a read cursor under participant authorization. Polling is enough for the first version. |
| `acceptOwnerReply(binding, reply)` | Require owner context and approved plugin permission where applicable. Atomically store the first initial reply and one durable delivery obligation. Return the recorded winner to both callers in a race. Append explicit follow-ups independently. |
| `acknowledgeReply(questionId, replyId, receiptId)` | Use the authenticated original Chat, or a host event with equivalent handoff evidence. Persist and expose the resulting receipt or a delivery failure. Retry addresses the original obligation and keeps the same reply ID and origin. |

Use the native Item’s stable UID, ask event ID, and ask-line index when applicable, scoped to its host. The numeric Item label is for display. Upstream derives line IDs as `eventId:index`. Keep these mappings separate from Inbox package, question, request, reply and receipt IDs. Store the accepted owner event ID and the transport message ID as separate observations. Orca can resolve native Item ownership to a Chat lineage root after `/clear`. V1 should bind the exact authenticated origin until a successor policy is explicitly approved and verified. [Upstream question identifiers](https://github.com/stablyai/orca/blob/374693b1414ad73e8c41846b715cd04e026db118/src/shared/bots/bot-item-question-answers.ts) · [Chat ownership](https://github.com/stablyai/orca/blob/374693b1414ad73e8c41846b715cd04e026db118/src/main/runtime/rpc/methods/bots-items-caller.ts)

Upstream owner comments use a transaction and deduplicate by request ID within the Item. A retry does not check changed content. The stale-ask guard applies when an ask is active. Once a single ask settles, a second distinct write can still append a comment and owe mail. The Inbox first-answer rule therefore needs its own canonical slot in the shared native and plugin transaction. [Upstream owner transaction](https://github.com/stablyai/orca/blob/374693b1414ad73e8c41846b715cd04e026db118/src/main/bots/bot-items-owner.ts)

| Example | Expected result |
| --- | --- |
| Repeat request `req-1` with the same contents and authenticated origin | Return the existing package and question IDs. Changed contents or a different binding produce a conflict. |
| Native submits `reply-A` while Inbox submits `reply-B` for `q-1`, and A commits first | Both receive A as the canonical initial answer. Only A gets an outbox obligation. Reusing an ID with changed contents or binding is a conflict. |
| Mail accepts `reply-A` to `(paired-a, studio, chat-7)` | The response can record a transport message ID. The reply remains **Submitted / awaiting confirmation**. |
| Receipt `receipt-1` names `q-1` and `reply-A`, authenticated as `(paired-a, studio, chat-7)` | Mark A **Agent received**. Replaying the identical receipt returns the same result. A receipt from `(local, studio, chat-7)`, another question, or a follow-up changes nothing about A. Reusing the same receipt ID with a different binding is a conflict. |

The Inbox backend can proceed with injected trust and transport adapters, access-checked list/detail and review requests, durable winner selection, mismatch conflicts, append-only follow-ups, and a persisted outbox and receipt reducer exercised against shared fixtures. The upstream issue covers part of the plugin API. Ordinary workspace ingress, canonical first acceptance and exact-origin receipt evidence remain release dependencies.

## Deferred desktop and paired-server acceptance

1. Prepare two local project workspaces and a workspace on a paired Orca server. Include a local and paired workspace with the same fixture workspace ID or alias. Use supported Claude and Codex workspace Chats across the runs. Record the desktop build, plugin API, server build, authenticated caller context and exact origin identifiers.
2. From a local workspace Chat, submit one disposable question through the supported submission entry point. Record package, request, question, Item UID and ask event IDs. Confirm the Inbox and native **Needs you** show the same question. Retry the identical submission and try changed content under the original ID.
3. Answer once from Inbox and once from native **Needs you** on a fresh question. On another fresh question, race different answers from both surfaces. Verify both display one winning reply ID, exactly one initial reply routes, and retries preserve it. Submit a follow-up and verify that it has an independent delivery record and receipt.
4. From the other local project open the first project's review in **All workspaces**. Verify the review becomes visible without changing workspace focus, with a pinned decision and unsent draft already open. Switch focus and scope and verify the draft stays with its question. Check that an unauthorized participant cannot read private snapshot bytes.
5. Repeat submission and answer on the paired server. Capture the accepted write, transport acceptance, and per-reply receipt from the original Chat as separate evidence. Confirm the local workspace with the same ID gets nothing. Disconnect and restart around a pending reply. Verify persistent state and same-ID retry, then close the original Chat and confirm failure without fallback. Check a wrong-origin or wrong-reply acknowledgement leaves the intended reply unconfirmed.
6. Verify both supported agents apply the effective workspace policy and can continue unaffected work. Follow the source issue or spec to the decision link and recorded outcome. Save the observed results against the [approved release gate](v1-spec.md#release-gate) and [acceptance matrix](implementation-handoff.md#acceptance-matrix).
